# 오류 게이트

한 번 난 오류를 기록해서 같은 경로로 다시 가지 않게 해요. 사용자가 승인한 게이트만 여기에 올려요.
해제할 때는 지우지 않고 상태를 "해제 (날짜, 사유)"로 바꿔요.

활성 게이트: **G-1, G-2** (2026-11-12 기준)

---

### G-1 | [스타일] 상태 색은 흑백에서도 구분되게

- 상태: 활성
- 등록: 2026-11-10 / 피뢰침 프론트 (지시문 2 다크 서재)
- 발생 상황: 책 블록을 다크 서재 재질로 바꾼 뒤 흑백 캡처에서 완료(회색 #94A3B8)와 안정(초록 #10B981)이 같은 밝기라 구분되지 않음
- 원인: 두 색의 밝기가 거의 같고, 정의서 4-5에서 둘 다 '꽉 채움'이라 패턴 차이도 없음
- 금지 경로: 색만 바꿔서 상태를 구분하기. 밝기가 비슷한 두 상태에 같은 패턴·같은 장식(금장 띠 등)을 주기
- 대신 할 것: 밝기 차이나 패턴·장식 차이로 구분을 보장하고, 책 위에 상태 글자를 함께 보임 (NF-06)
- 사전 체크: 상태를 추가하거나 상태 색·책 재질을 바꿀 때마다 `/dev`의 책 블록 6개를 `filter: grayscale(1)`로 확인

### G-2 | [API연동] 기준 명세를 양쪽이 확인하기 전에 연결 작업을 시작하지 않기

- 상태: 활성
- 등록: 2026-11-12 / 피뢰침 프론트 (실제 API 연결)
- 발생 상황: 백엔드 OpenAPI v0.7.0을 받아 API 층을 그 명세로 바꾸는 연결 작업을 시작했는데, 같은 날 백엔드가 프론트 API 초안(docs/api-draft.md)에 맞추기로 바꿔 작업을 롤백함
- 원인: 어느 쪽 명세를 기준으로 할지 백엔드와 확정하지 않은 채, 받은 명세로 바로 연결 작업을 시작함
- 금지 경로: 상대 팀 명세를 받자마자 기준 확인 없이 API 층(client · endpoints · adapters · mocks) 수정에 들어가기
- 대신 할 것: 기준 명세가 누구 것인지와 공통 규칙(주소 · 응답 틀 · 인증)을 백엔드 회신으로 확인하고 docs에 적은 뒤 시작. 큰 수정 전에는 보관 브랜치를 먼저 만듦
- 사전 체크: API 층을 바꾸는 지시문 전에 '기준 명세 확인 회신이 있는가'

## 형식

### G-번호 | [영역] 한 줄 제목

- 상태: 활성
- 등록: YYYY-MM-DD / 프로젝트명
- 발생 상황: 어떤 작업 중 어떤 증상이 났는지
- 원인:
- 금지 경로: 다시 하지 말아야 할 방법·코드·설정
- 대신 할 것: 올바른 방법
- 사전 체크: 비슷한 작업 전에 확인할 것

영역 예: 배포 / Git / React / API연동 / AI연동 / 환경설정 / 스타일
